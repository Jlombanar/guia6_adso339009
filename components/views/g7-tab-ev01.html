Informe técnico de plan de trabajo para construcción de software

Antes de escribir código se decide cómo se va a construir el software y con qué herramientas se controlarán sus versiones. En esta evidencia elaboras un informe técnico con el plan de trabajo de la Guía 7 y la selección de las herramientas de versionamiento. El ejemplo resuelto es el plan de la tienda deportes que se viene trabajando desde la Guía 6, con Node.js y Express en el back-end y React en el front-end.

Criterio de evaluación

Interpreta el informe de diseño para definir el plan de trabajo, selecciona y configura herramientas de desarrollo según el software a construir y define estándares de acuerdo con la plataforma. Instrumento: lista de chequeo IE-GA7-220501096-AA1-EV01. El producto es un informe técnico en PDF con, como mínimo, portada, introducción, objetivo y la selección de herramientas de versionamiento.

Concepto 1

¿Qué lleva un plan de trabajo?

Es la hoja de ruta de la construcción. Responde qué se construye, en qué orden, con qué tecnologías y cómo se va a controlar el código.

Qué se construye

Los módulos del software, sacados de los requerimientos y de los artefactos de diseño: casos de uso, diagrama de clases, base de datos y prototipos.

En qué orden

Un cronograma por sprints que sigue las actividades de la guía: acceso a datos y formularios (AA2), módulos en capas (AA3), React (AA4) y API (AA5).

Con qué herramientas

Lenguaje, framework, base de datos, IDE y herramientas de prueba, con el uso que tendrá cada una en el proyecto.

Cómo se versiona

La parte central de esta evidencia: sistema de control de versiones, plataforma remota, ramas, commits y etiquetas.

Concepto 2

Sistemas de control de versiones

Registran cada cambio del código: quién lo hizo, cuándo y por qué. Permiten volver atrás, trabajar en paralelo y tener una copia en la nube. Hay dos tipos:

Sistemas centralizados frente a distribuidos
Criterio Centralizado (Subversion) Distribuido (Git)
Dónde está el historial Solo en el servidor Copia completa en cada equipo
Trabajo sin internet No permite hacer commits Permite commits, ramas e historial
Ramas Costosas; se usan poco Rápidas y livianas; una por funcionalidad
Si falla el servidor Se puede perder el historial Cualquier copia restaura el proyecto

Git es el sistema; el repositorio remoto vive en una plataforma. Estas son las tres más usadas:

Comparativa de plataformas para el repositorio remoto
Criterio GitHub GitLab Bitbucket
Repositorios privados gratis Sí, ilimitados Sí, ilimitados Sí, hasta 5 usuarios
Integración continua GitHub Actions GitLab CI/CD Bitbucket Pipelines
Gestión de tareas Issues y Projects Issues y tableros Integración con Jira
Comunidad y portafolio La más grande Grande Menor

Selección del ejemplo: Git + GitHub

Git porque es distribuido, gratuito y el estándar de la industria, y porque lo piden las evidencias AA1-EV03 a EV05. GitHub porque en un solo lugar reúne el código, las tareas (Issues y Projects) y la integración continua (Actions), y el repositorio queda como portafolio. GitLab es igual de válido si tu instructor lo prefiere.

Concepto 3

Estrategia de versionamiento

Elegir la herramienta no basta: el informe debe decir cómo se va a usar. Son cuatro decisiones:

Modelo de ramas

main estable, develop para integrar y una rama feature/… o fix/… por cada tarea, que entra con pull request.

Mensajes de commit

Conventional Commits: feat: agregar registro de productos, fix: validar stock, docs: actualizar README.

Versiones y etiquetas

Versionado semántico: cada actividad terminada se marca con una etiqueta, de v0.1.0 (AA1) a v1.0.0 (AA5).

Archivos del repositorio

.gitignore para no subir target/, node_modules/ ni contraseñas, y un README.md que explique el proyecto.

Paso a paso

Cómo elaborar el informe

Ten a la mano los artefactos de tu proyecto formativo: requerimientos, casos de uso, diagrama de clases, base de datos y prototipos.

  1. Describe el software

    Qué problema resuelve, para quién y la tabla de requerimientos funcionales con las tablas de la base de datos que usa cada uno.

  2. Define los módulos y el cronograma

    Relaciona cada actividad de la guía con el módulo que construirás y su tecnología. Reparte las 498 horas en sprints de dos semanas, con un resultado concreto por sprint.

  3. Lista las herramientas de desarrollo

    Una tabla con categoría, herramienta y uso: Node.js y npm, Express, mysql2, EJS, MySQL, React, ESLint, VS Code y Postman. Consulta la versión estable vigente en el sitio de cada una.

  4. Compara y selecciona el versionamiento

    Haz las dos tablas del Concepto 2 (tipos de sistema y plataformas) y justifica tu elección con las necesidades de tu proyecto. Es el contenido mínimo que pide la guía.

  5. Escribe la estrategia de versionamiento

    Estructura del repositorio, modelo de ramas con su diagrama, convención de commits, etiquetas, .gitignore y el flujo de comandos de un día de trabajo.

  6. Agrega integración continua y seguridad

    Un workflow de GitHub Actions que compile el proyecto en cada push, y las reglas para proteger ramas y no subir credenciales.

  7. Arma y exporta el documento

    Portada, contenido, introducción, objetivos, los apartados anteriores, conclusiones y referencias. En Word usa los estilos Título 1 y Título 2 y exporta con Archivo › Guardar como › PDF.
