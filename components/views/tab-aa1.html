GA6-220501096-AA1 · Crear un modelo de base de datos

"Crear un modelo de base de datos, con base a los requerimientos del cliente." Esta actividad busca que antes de escribir una sola línea de SQL, sepas pensar los datos: qué entidades existen, cómo se relacionan entre sí, y cómo evitar que la información quede duplicada o inconsistente.

Evidencia Qué pide
EV01 Resolución de problemas aplicando el modelo relacional, cardinalidad y normalización
EV02 Elaboración del modelo entidad-relación (MER) de un caso propuesto
EV03 Creación de objetos en una base de datos no relacional (estructura de un documento JSON)
EV04 Elaboración de una base de datos en MongoDB
Concepto 1

¿Qué es el modelo relacional?

Es una forma de organizar la información en tablas (también llamadas relaciones). Cada tabla representa una entidad del mundo real (un cliente, un producto, un pedido), cada columna es un atributo, y cada fila es un registro concreto.

🧱 Las piezas básicas de una tabla

Entidad → se convierte en una tabla (ej: Cliente, Producto).
Atributo → se convierte en una columna (ej: nombre, precio).
Llave primaria (PK) → columna que identifica de forma única cada fila (ej: id_producto).
Llave foránea (FK) → columna que apunta a la llave primaria de otra tabla, y es lo que crea la relación entre ambas.

🍔 Ejemplo aplicado a tu proyecto "Fast Food Paradise": en vez de guardar todo en una sola tabla gigante donde se repite el nombre del cliente en cada pedido, separamos la información en tres entidades relacionadas: Clientes, Productos y Pedidos.
-- Tabla Clientes id_cliente INT PK nombre VARCHAR(80) telefono VARCHAR(15) direccion VARCHAR(120)
-- Tabla Productos id_producto INT PK nombre VARCHAR(60) precio DECIMAL(10,2) categoria VARCHAR(40)
-- Tabla Pedidos (une a las otras dos) id_pedido INT PK id_cliente INT FK → referencia a Clientes id_producto INT FK → referencia a Productos cantidad INT fecha DATE
Concepto 2

¿Qué es la cardinalidad?

La cardinalidad describe cuántas veces puede relacionarse un registro de una entidad con registros de otra entidad. Es la regla de negocio detrás de la relación.

1 : 1 (uno a uno)

Un registro de A se relaciona con exactamente un registro de B, y viceversa.

Ej: un Cliente tiene una única Cuenta de fidelización.

1 : N (uno a muchos)

Un registro de A se relaciona con varios de B, pero cada B solo pertenece a un A.

Ej: un Cliente hace muchos Pedidos, pero cada Pedido es de un solo Cliente.

N : M (muchos a muchos)

Varios registros de A se relacionan con varios de B. Se resuelve con una tabla intermedia.

Ej: un Pedido puede tener muchos Productos, y un Producto aparece en muchos Pedidos.

🍔 Aplicado a Fast Food Paradise

Cliente → Pedido es 1:N (un cliente hace muchos pedidos).
Pedido → Producto en realidad es N:M (un pedido puede llevar varios productos —una hamburguesa y una gaseosa— y un mismo producto, como la gaseosa, aparece en muchos pedidos distintos). Para resolver ese N:M se crea una tabla intermedia, por ejemplo Detalle_Pedido, que guarda id_pedido + id_producto + cantidad.

Concepto 3

¿Qué es la normalización?

Es el proceso de organizar las tablas para eliminar redundancia (datos repetidos) e inconsistencias. Se aplica por niveles llamados "formas normales".

  • 1FN — Primera Forma Normal

    Cada columna debe tener un solo valor (atómico), y no deben existir columnas repetidas o listas dentro de una celda. Nada de guardar "hamburguesa, gaseosa, papas" en una sola casilla.

  • 2FN — Segunda Forma Normal

    Cumple 1FN, y además cada columna que no es llave debe depender de toda la llave primaria, no solo de una parte (esto aplica cuando la llave primaria tiene varias columnas).

  • 3FN — Tercera Forma Normal

    Cumple 2FN, y además ninguna columna que no es llave puede depender de otra columna que tampoco es llave (sin dependencias transitivas).

    • 🍔 Ejemplo antes y después, con tu proyecto:
    ❌ SIN normalizar (una sola tabla "Pedido")
    id_pedido cliente telefono_cliente productos
    1 Ana Pérez 3001234567 Hamburguesa, Gaseosa
    2 Ana Pérez 3001234567 Papas

    ⚠️ El teléfono de Ana se repite en cada pedido (redundancia) y la columna "productos" guarda varios valores en una celda (viola 1FN).

    ✅ Normalizada (3 tablas relacionadas)
    Clientes Pedidos Detalle_Pedido
    id_cliente, nombre, telefono id_pedido, id_cliente, fecha id_pedido, id_producto, cantidad

    ✔ El teléfono de Ana se guarda una sola vez. Cada pedido puede tener varios productos sin repetir filas innecesarias.

    📖 Cómo leer este diagrama

    Un Cliente (1) puede hacer muchos (N) Pedidos. Cada Pedido (1) puede tener muchas (N) líneas en Detalle_Pedido, y cada línea apunta a un (1) Producto — así se resuelve de forma limpia la relación N:M entre Pedido y Producto que vimos en el concepto de cardinalidad.

    Concepto 5

    Bases de datos NoSQL y MongoDB

    No todo se modela en tablas. Una base de datos NoSQL como MongoDB guarda la información en documentos con formato JSON, agrupados en colecciones (el equivalente a una tabla, pero flexible: no todos los documentos tienen que tener las mismas columnas).

    Relacional (SQL) No relacional (MongoDB)
    Base de datos Base de datos
    Tabla Colección
    Fila / registro Documento (JSON)
    Columna Campo (field)
    Llave primaria (id) _id (generado automáticamente)
    🍔 Ejemplo: así se vería un producto de Fast Food Paradise como documento dentro de una colección productos en MongoDB:
    { "_id": "6523af9b", "nombre": "Hamburguesa Clásica", "precio": 9000, "categoria": "hamburguesas", "disponible": true, "ingredientes": ["pan", "carne", "queso", "lechuga"] }

    💡 ¿Por qué aquí sí podemos meter una lista en un campo?

    A diferencia del modelo relacional (donde eso violaba la 1FN), en NoSQL es normal y está permitido anidar listas o incluso documentos dentro de otros — por eso se dice que MongoDB es un modelo "orientado a documentos", pensado para datos flexibles que no siempre tienen la misma forma.
