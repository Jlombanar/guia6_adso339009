Creación de la estructura de la BD y aplicación de restricciones

Pasa del modelo entidad relación a la base de datos física: define cada tabla con sus tipos de datos y protege la información con llaves primarias, llaves foráneas y campos obligatorios. El ejemplo resuelto es la base deportes de una tienda de artículos deportivos.

Criterio de evaluación

Implementa restricciones en la base de datos de acuerdo con las reglas de diseño. Instrumento: lista de chequeo IE-GA6-220501096-AA2-EV02. El producto es un archivo ZIP con el documento en Word y los archivos de MySQL Workbench (.mwb) con los diseños entidad relación.

Concepto 1

¿Qué es una restricción?

Una restricción (constraint) es una regla que el motor verifica en cada INSERT, UPDATE o DELETE. Si la operación la incumple, MySQL la rechaza con un error y el dato inválido nunca llega a la tabla.

Restricciones usadas en la base deportes
Restricción Qué garantiza Ejemplo en deportes
PRIMARY KEY Cada fila tiene un identificador único y no nulo. Users.id_user
AUTO_INCREMENT MySQL asigna el siguiente número de la llave automáticamente. productos.Id_producto
FOREIGN KEY El valor existe en la tabla referenciada (integridad referencial). pedido.id_user → Users
NOT NULL El campo es obligatorio. Todos los campos del modelo

Comportamiento de las llaves foráneas

Sin ON DELETE ni ON UPDATE, MySQL aplica RESTRICT: no deja crear un pedido para un usuario que no existe ni borrar un usuario que ya tiene pedidos. Como las llaves foráneas no llevan nombre, MySQL las llama pedido_ibfk_1, detalle_pedido_ibfk_1 y detalle_pedido_ibfk_2.

Concepto 2

Lectura del modelo entidad relación

Cuatro entidades. La relación muchos a muchos entre pedidos y productos se resuelve con la tabla intermedia detalle_pedido.

Users 1 ── N pedido

Un usuario hace muchos pedidos; cada pedido pertenece a un usuario.

pedido 1 ── N detalle_pedido

Un pedido tiene varias líneas de detalle, una por producto.

productos 1 ── N detalle_pedido

Un producto puede aparecer en el detalle de muchos pedidos.

Correo VARCHAR(10)

El campo admite máximo diez caracteres. Usa correos cortos en los datos de prueba (lg@mail.co); uno más largo genera el error 1406.

Ejemplo resuelto

Script de la base de datos deportes

Crea primero las tablas padre (Users, productos) antes de las hijas que las referencian: una llave foránea solo puede apuntar a una tabla que ya existe.

  1. Crea la base de datos

    CREATE DATABASE deportes;
USE deportes;

  2. Tabla Users

    CREATE table Users(
    id_user INT PRIMARY KEY AUTO_INCREMENT,
    NOmnbre VARCHAR(100) NOT NULL,
    Edad int NOT NULL,
    Correo VARCHAR(10) NOT NULL,
    Passwords VARCHAR(100) NOT NULL
);

  3. Tabla pedido

    Cada sentencia termina en punto y coma; sin él, Workbench une esta tabla con la siguiente y da error de sintaxis. 

    CREATE TABLE pedido(
    Id_pedido INT PRIMARY KEY AUTO_INCREMENT,
    id_user INT NOT NULL,
    Fecha DATE NOT NULL,
    FOREIGN KEY (id_user) REFERENCES Users(id_user)
);

  4. Tabla productos

    DECIMAL(10,2) guarda el precio exacto, sin los errores de redondeo de FLOAT. 

    CREATE TABLE productos(
    Id_producto INT PRIMARY KEY AUTO_INCREMENT,
    Nombre VARCHAR(100) NOT NULL,
    Precio DECIMAL(10,2) NOT NULL,
    Stock INT NOT NULL
);

  5. Tabla detalle_pedido

    Dos llaves foráneas: una hacia el pedido y otra hacia el producto.

    CREATE TABLE detalle_pedido (
    Id_detalle INT PRIMARY KEY AUTO_INCREMENT,
    Id_pedido INT NOT NULL,
    Id_producto INT NOT NULL,
    Cantidad INT NOT NULL,
    FOREIGN KEY (Id_pedido) REFERENCES pedido(Id_pedido),
    FOREIGN KEY (Id_producto) REFERENCES productos(Id_producto)
);

  6. Verifica la estructura y las restricciones

    Captura estos resultados para el documento: deben aparecer 7 restricciones, 4 llaves primarias y 3 foráneas. 

    SHOW TABLES;
DESCRIBE pedido;

SELECT TABLE_NAME, CONSTRAINT_NAME, CONSTRAINT_TYPE
FROM information_schema.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = 'deportes'
ORDER BY TABLE_NAME, CONSTRAINT_TYPE;
Demuestra que funcionan

Pruebas de las restricciones

Inserta primero algunos usuarios, productos y pedidos. Luego ejecuta cada sentencia por separado: todas deben fallar, y ese error es la evidencia de que la restricción protege los datos.

Sentencias de prueba y error esperado
Sentencia Error esperado
INSERT INTO Users (id_user, NOmnbre, Edad, Correo, Passwords) VALUES (1, 'Repetido', 20, 'x@mail.co', 'x'); 1062 · llave primaria duplicada
INSERT INTO productos (Nombre, Precio, Stock) VALUES (NULL, 1000, 1); 1048 · Nombre no puede ser nulo
INSERT INTO pedido (id_user, Fecha) VALUES (99, '2026-10-21'); 1452 · el usuario 99 no existe
INSERT INTO detalle_pedido (Id_pedido, Id_producto, Cantidad) VALUES (1, 99, 1); 1452 · el producto 99 no existe
DELETE FROM Users WHERE id_user = 1; 1451 · el usuario tiene pedidos
